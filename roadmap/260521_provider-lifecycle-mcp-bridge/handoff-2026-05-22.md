## Key Decisions To Preserve

- The installed coordinator root gets one runtime venv:

  ```text
  ar-coordination/.venv
  ```

- Normal MCP harness config points to that venv's Python:

  ```text
  /path/to/ar-coordination/.venv/bin/python -m agents_remember.mcp
  ```

- The user should not repeat `--coordination-root` in normal MCP config. The MCP runtime should infer the coordinator root from the installed runtime/venv location. Explicit overrides are for tests, workbenches, and debugging.
- Runtime/MCP dependencies are owned by Agents Remember source code, not by provider dependency handling:

  ```text
  source:    agents-remember-md/runtime/requirements.txt
  installed: ar-coordination/requirements.txt
  venv:      ar-coordination/.venv
  ```

- Root source `agents-remember-md/requirements.txt` remains source/dev tooling only. It currently contains Ruff/Radon.
- Provider dependencies remain separate because providers are third-party code:

  ```text
  ar-coordination/providers/requirements/...
  ar-coordination/providers/_venvs/...
  ```

- Phase 1 proves Codex first. Claude Code and the rest of the harness-specific docs belong to add-on A1 unless the developer explicitly promotes one into the active slice.
- Provider status should be both:
  - an input to `context.packet`
  - a later standalone quick-check tool
- The exact public tool name is still open: maybe `provider.status` in docs, or `provider_status` if MCP SDK/tool naming rules require identifier-style names.
