# Correct-input write refusal — the same-tool ladder

Read this procedure when a writer or record tool refuses a correct write. Use the primary tool
first. If the refusal names a fault in your input, correct that input through the same tool.
A missing tool or unadmitted capability is not a refused correct write; report that missing
capability and what remains unwritten.

For a correct-input write refusal (D627; D631 Q25–Q26):

1. **Check the build and route.** Compare the serving build, the invoked build and the admitted
   target and input shape. Retain the tool's actual refusal. For the Curator's CLI binding, use
   the command procedure in `curator-writer-details.md`.
2. **Take an honest route the tool admits.** Keep the claim true, the serving build and the
   target authority. Record each input and refusal; a route that requires hidden edits, an older
   build lacking a check, false tool authorship or a weakened false claim is no route.
3. **Otherwise make that write openly by hand.** Tell the record's or machine state's owner
   before writing. This exception covers only the same tool and input class that refused;
   every other write still uses its tool. Record the manual write and its provenance, run every
   check that still works, and record the defect in an issue row. Put the tool, every input tried,
   every refusal, the actual write, all check results and that issue row in the full report. Claim no
   tool receipt for the manual work. The tool repair is a separate task when the developer slots it; the next Curator
   re-records the affected knowledge.

When admitted to your role, the covered record writes are `knowledge_write` or admitted
`knowledge-ingest`, `citation_fix`,
`citation_note_revision`, `curator_coherence` publish and `task_doc` edits, including
`append_decision`, `begin_review`, `record_review` and `record_route_review`.

For a refused correct `task_doc` edit, record the attempted inputs and refusal, notify the owner,
and amend the canonical document openly. The owner's next `task_doc` publication refreshes
renders and projections; rendered copies are never parsed back. Use the product tool first for task retirement or folder movement. On refusal of correct input, follow the D627/D631 ladder: record the refusal, tell the owner and perform the logged manual step. Do not retain a blanket ban on hand movement.
The task-folder exception covers only the refused retirement or movement step, never a Git commit or another transaction step. This procedure gives Bootstrap no new writer, task-document or migration duty.

**The stops remain.** Read, check, validation and sync refusals, starts, product guards and commit
gates retain their boundaries. Repair validator and gate findings under D229; this write ladder
does not waive them. A denied or unanswered permission request is not worked around through
another tool, command, helper or later turn (D632). Other tools and input classes retain their
normal routes.
