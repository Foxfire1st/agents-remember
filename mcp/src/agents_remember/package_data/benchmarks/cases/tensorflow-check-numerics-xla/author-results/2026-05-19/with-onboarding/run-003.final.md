**Triage Result**
The report matches the pinned source. This is most likely an XLA compiler-path elision of `CheckNumerics`, not a Python API or eager/runtime kernel issue.

Subsystem boundaries involved:

- Python frontend: `tf.function(jit_compile=True)` sets `_XlaMustCompile` in `tensorflow/python/eager/polymorphic_function/polymorphic_function.py:637`.
- Normal runtime: `CheckNumerics` is stateful in `tensorflow/core/ops/array_ops.cc:1387`, and the CPU/GPU kernels scan values and set `InvalidArgumentError` in `tensorflow/core/kernels/check_numerics_op.cc:88`.
- XLA/JIT policy: XLA device registrations enable `elide_assert_and_checknumerics` for CPU/GPU/TPU (`xla_cpu_device.cc:79`, `xla_gpu_device.cc:96`, `xla_tpu_device.cc:363`).
- XLA lowering: `CheckNumerics` is registered to `MlirXlaOpKernel` in `tensorflow/compiler/tf2xla/kernels/check_numerics_op.cc:21`, then MLIR legalization rewrites it to its input value.

Most likely cause: XLA does not implement native `CheckNumerics` error semantics. The source says this directly: `xla_op_registry.h:168` notes Assert/CheckNumerics are elided because XLA does not natively support them, and `compilability_check_util.h:108` calls their XLA implementation a dummy implementation. The concrete legalization pattern confirms the behavior: `tensorflow/compiler/mlir/tf2xla/transforms/legalize_tf_patterns.td:397` has `TODO: Support CheckNumerics in HLO`, and line `399` replaces the op with its operand. The StableHLO path has the same pattern at `stablehlo/transforms/legalize_tf_patterns.td:389`.

So eager and `jit_compile=False` reach the real core kernel and raise; `jit_compile=True` routes through XLA, where the check is intentionally lowered away, so NaN/Inf pass through. The fix boundary is the TensorFlow compiler/XLA legalization path: either add faithful HLO/XLA support for numeric-check failure semantics or stop silently compiling/eliding this op when it is used as a safety guard. Source files were not edited.
