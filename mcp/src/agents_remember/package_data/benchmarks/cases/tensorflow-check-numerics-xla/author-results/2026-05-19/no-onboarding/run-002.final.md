**Verdict**

The ticket is credible and matches the pinned source. This is most likely an XLA lowering limitation, not a Python API or eager runtime issue.

`tf.debugging.check_numerics` maps to the `CheckNumerics` op, whose normal CPU/GPU kernels scan the tensor and set `InvalidArgumentError` on NaN/Inf. See `core/ops/array_ops.cc:1387`, `core/kernels/check_numerics_op.cc:102`, and the MLIR op contract at `compiler/mlir/tensorflow/ir/tf_generated_ops.td:2109`.

**Subsystem Boundaries**

- Python tracing/API: `tf.function(jit_compile=True)` sets `_XlaMustCompile` in `python/eager/polymorphic_function/polymorphic_function.py:638`.
- Core runtime kernels: `core/kernels/check_numerics_op.cc` implements the actual finite-value checks for non-XLA execution.
- XLA bridge / TF2XLA: `compiler/tf2xla/kernels/check_numerics_op.cc:21` registers `CheckNumerics` as an `MlirXlaOpKernel`.
- MLIR TF-to-HLO legalization: `compiler/mlir/tf2xla/transforms/legalize_tf_patterns.td:397` and `compiler/mlir/stablehlo/transforms/legalize_tf_patterns.td:389`.

**Most Likely Cause**

The XLA legalization explicitly elides the check. Both TF2XLA and StableHLO legalization contain:

- `TODO(b/32223192): Support CheckNumerics in HLO`
- a pattern rewriting `TF_CheckNumericsOp` to `replaceWithValue $op`

The test confirms this expected lowering: `compiler/mlir/tf2xla/tests/legalize-tf.mlir:1300` checks that a function containing `tf.CheckNumerics` legalizes to `return %arg0`.

This also aligns with JIT comments in `compiler/jit/compilability_check_util.h:111`: implicit XLA avoids surprising users by not clustering Assert/CheckNumerics, but explicit XLA may use dummy implementations. XLA device registrations enable that elision in `xla_cpu_device.cc:79`, `xla_gpu_device.cc:96`, and `xla_tpu_device.cc:363`.

So under `jit_compile=True`, `CheckNumerics` becomes an identity/pass-through in the compiled HLO path, letting NaN/Inf through silently. Under eager and `jit_compile=False`, the normal TensorFlow kernel runs and raises as expected.
