Subsystem boundaries involved:

- Python frontend: `tf.function(jit_compile=True)` sets `_XlaMustCompile`.
- TensorFlow core runtime: `CheckNumerics` op definition and CPU/GPU kernels implement the raising behavior.
- XLA/tf2xla registration: `CheckNumerics` is routed to MLIR XLA lowering, not the runtime kernel.
- MLIR TF2XLA/StableHLO legalization: `CheckNumerics` is currently elided to identity.
- XLA compilability policy: comments in [compilability_check_util.h](/C:/ew/ar-coordination/benchmarks/workspaces/tensorflow-check-numerics-xla/with-memory/repos/tensorflow/tensorflow/compiler/jit/compilability_check_util.h:108) state Assert/CheckNumerics have dummy XLA implementations; [xla_op_registry.h](/C:/ew/ar-coordination/benchmarks/workspaces/tensorflow-check-numerics-xla/with-memory/repos/tensorflow/tensorflow/compiler/tf2xla/xla_op_registry.h:168) says XLA does not natively support them.

Most likely cause: explicit XLA compilation intentionally lowers `CheckNumerics` as a no-op/identity because HLO lacks native side-effecting `CheckNumerics` support. That preserves tensor flow but drops the numerical safety check, so NaN/Inf values pass through under `jit_compile=True`.
