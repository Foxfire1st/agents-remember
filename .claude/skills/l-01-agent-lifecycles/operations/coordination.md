# Operation — Coordination

Use native Orca as the execution owner. Consult the active runtime's `orca-cli` and `orchestration` skill before invoking Run, Task/Spec, Dispatch, terminal reuse, or messaging. Establish a native Run when the work requires a durable coordinator; bind each native task to its exact canonical AR task and requirement. Orca's sender identity is runtime-provided. Address only actual native recipients/IDs returned by Orca.

Choose a flat graph for small work: Architect directly assigns distinct Workers, Reviewers, and Curators. For a larger sprint, an Orchestrator may coordinate; a Manager may own one selected master. These roles are optional according to scale.

Establish one native Run for the approved work, or reuse the already selected Run. For each distinct leaf role, call `orca_role_prepare` with the exact canonical sprint, master, and leaf references. It resolves or creates the AR paired enclosure, writes the complete role handover beside the task report, and starts an idle Orca session through the native launch boundary. It does not create a native Run, Task, or Dispatch and the role has not started work yet. Use its returned handover path and SHA-256, workspace selector, terminal handle, and task spec as-is. If it reports an uncertain start, retry the same `requestId` or reconcile the existing native receipt before creating another session.

Use the same native Run for the role sequence. Start each Task/Dispatch with native `worker-start` and the returned workspace selector, terminal handle, and spec. Capture raw `--json` stdout for Run creation and each Task/Dispatch operation byte-for-byte under the returned task report directory, using only exact Orca IDs in filenames. A `worker-start` serving an AR leaf must use the returned native terminal and the already configured paired worktree; do not create an independent Orca Git worktree.

After a Reviewer rejects a candidate, continue on the same native Worker terminal with a follow-up Task spec that identifies the exact finding IDs and report path. Keep the same candidate class and contract baseline, and verify each finding. Launch distinct Reviewer and Curator sessions for their work. Keep paired code/memory/report paths and exact task references in every handover.

Use `orchestration.send`, `check`, and `reply` only as documented by the installed native skill. Preserve message, Run, Dispatch, task, terminal, and recipient IDs in the durable handover. Continue Orca's own check/wait and response loop until assigned work is complete, blocked, or a true developer decision is needed; do not dispatch and stop. On an uncertain peer delivery, reconcile the same operation; do not guess a parent or launch duplicate work. A manual role can work directly with the current user without a parent reference.

Re-evaluate work from canonical AR task facts and actual evidence when invoked. Do not create background polling or a second scheduler. A native task/run is execution metadata, never a second requirements, review, curation, or acceptance ledger.
