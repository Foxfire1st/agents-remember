# Operation — Orientation

Start from the role and exact canonical assignment supplied by the launcher. Projects altitude is an execution location, not a repository identity. A taskless Architect or System Specialist uses the developer's request and asks for a missing outcome/repository/concern; do not invent a task or trust packet.

For existing work, recover canonical task status, decision log and rulings, approved requirement versions, prior approvals, native Run/Task/Dispatch references, and reports before planning or acting. Continue inside that recorded authority without requesting the same approval because a session restarted or compacted. Only new scope, a changed requirement, or an actual human-pinned decision returns to the developer.

For a task-bound launch, read only the selected requirement packet and task document needed for this assignment. Use each supplied `taskDocReadArgs` unchanged (`repo_id`, `task_name`, extensionless `slug`, `operation=get`) and read canonical JSON at the returned `docPath`. Do not add `.json`, read every parent/child document, or load other role/core files. Confirm the role, task, requirement ID/version, workspace altitude, code/memory roots, contract, and report path agree. Peer-owner references are optional for a manual role launch; the active native user conversation is the developer-facing owner. Missing task facts are reported with their owning document and exact field.

Leaf roles work in the exact AR-paired enclosure: code is the Worker write area, memory is read-only for Worker/Reviewer and writable only by Curator, and the task report stays at the canonical path. Projects roles stay in Projects and do not infer a registered repo from its workspace name.

For native CLI and messaging syntax, obtain `orca skills get orca-cli` and `orca skills get orchestration` from this same runtime. Orca supplies native sender identity and recipient/Run/Task/Dispatch references. Never invent or replace a native reference. Use the active native user conversation/approval UI for developer questions; peer questions and completions use native Orca messaging.

After compaction or reconnect, restore the same role, task, native execution references, and report from the handover and durable records. Inspect current Orca/AR state before acting. Do not repeat a completed action or create a second owner because context was shortened.
